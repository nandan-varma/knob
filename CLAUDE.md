## What this is

Knob is a native macOS 26+ (Tahoe) distraction blocker: block apps and websites via a menu bar app, with quick sessions, recurring schedules, strict mode, and a stats dashboard. Swift 6 + SwiftUI, deployment target macOS 26.0. Quick sessions are open-ended (they run until stopped; the UI shows elapsed time). Website blocking UI is gated by `FeatureFlags.websiteBlockingEnabled` (off until the NetworkExtension entitlement is approved). No tests.

The project file is **generated by XcodeGen** from `project.yml` — never hand-edit `Knob.xcodeproj`. Any change to targets, entitlements, Info.plist keys, or source paths goes in `project.yml`, then regenerate.

## Commands

```bash
# Regenerate the Xcode project after editing project.yml (or adding/removing source files
# in a way that changes directory structure — XcodeGen globs by folder, so plain new .swift
# files inside an already-listed folder don't need this)
xcodegen generate

# Compile-only check (fast, no signing needed) — use this while iterating on source changes
xcodebuild -project Knob.xcodeproj -scheme Knob -configuration Debug \
  -destination "platform=macOS" build CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO

# Full signed build (needed to actually run it, since AppBlocker/SessionManager require
# a running, launched app rather than just compiled code)
xcodebuild -project Knob.xcodeproj -scheme Knob -configuration Debug \
  -destination "platform=macOS" build -allowProvisioningUpdates

# Run the built app
open ~/Library/Developer/Xcode/DerivedData/Knob-*/Build/Products/Debug/Knob.app
```

No test target exists. No lint config (SwiftLint/SwiftFormat) is set up.

## Architecture

### Why this isn't built on Family Controls / Screen Time API

The obvious approach for a macOS blocker — Apple's `FamilyControls`/`ManagedSettings`/`DeviceActivity` stack — **does not exist for macOS apps**, despite the frameworks shipping in the macOS SDK. Every meaningful type (`ManagedSettingsStore`, `AuthorizationCenter`, `FamilyActivityPicker`, `ShieldSettings`) is `@available(macOS, unavailable)`, on both native macOS and Mac Catalyst. This was verified directly against the SDK's `.swiftinterface`/header files, not assumed — if you're ever tempted to reach for those frameworks here, check `@available(macOS` annotations in the actual SDK first (`/Applications/Xcode.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX*.sdk/System/Library/Frameworks/`).

What's used instead, per concern:

- **App blocking** (`Knob/Blocking/AppBlocker.swift`): `NSWorkspace` launch-notification monitoring + `terminate()`/`forceTerminate()`. No special entitlement. Only works while the Knob process is running — there's no OS-level persistence like a Family Controls shield would give, which is why the app is meant to run as a login item (`SMAppService`, wired in `SettingsView.swift`) and why "strict mode" is UI friction on the *unlock* path rather than an unkillable background mechanism.
- **Website blocking** (`KnobFilterExtension/FilterDataProvider.swift` + `Knob/Blocking/WebFilterController.swift`): a `NEFilterDataProvider` packaged as a macOS **System Extension** (not a classic `.appex` App Extension — Network Extension content filters on macOS use `NEProvider.startSystemExtensionMode()` and embed under `Contents/Library/SystemExtensions/`). `WebFilterController` in the main app activates it via `OSSystemExtensionRequest` and configures `NEFilterManager`/`NEFilterProviderConfiguration` once; after that, `handleNewFlow(_:)` in the extension just checks `ActiveBlockList.domains` (an App Group-shared `UserDefaults`) on every flow — no reconfiguration or extension restart needed when the block list changes.
- **Quick sessions and recurring schedules** (`Knob/Blocking/SessionManager.swift`): pure in-app timers (`Timer`, plus a 30s poll + wake-notification re-check for schedules), because there's no `DeviceActivity`-style OS scheduler available. This is the same "must keep running" constraint as app blocking.

### Process/data split

Three build products share state through **one mechanism**: an App Group (`group.com.nandanvarma.knob`), accessed via `Shared/SharedModelContainer.swift` (a SwiftData `ModelContainer` pointed at the App Group container URL) and `Shared/ActiveBlockList.swift` (App-Group `UserDefaults`, for the one value the sandboxed filter extension needs — kept separate from SwiftData deliberately, since Apple's own guidance for content filter extensions is to run the data provider in as restrictive a sandbox as possible and not hand it the full model store).

- **`Knob`** (main app, `MenuBarExtra` + a `WindowGroup`): owns the SwiftData store, all UI, `SessionManager` (the enforcement orchestrator), `AppBlocker`, `WebFilterController`.
- **`KnobFilterExtension`** (system extension, no UI): only `FilterDataProvider`, reading `ActiveBlockList.domains` per flow. Never touches SwiftData.
- **`Shared/`**: compiled into *both* targets from source (see `sources:` in `project.yml` — no shared framework target; that's the deliberate, simpler choice over the embedding/signing overhead of a separate framework for three small files).

### SwiftData models (`Shared/Models/`)

`BlockProfile` (named set of blocked bundle IDs + domains) → referenced by ID from `BlockSchedule` (weekday + time-of-day window, `Calendar.Component.weekday` numbering) and `FocusSession` (one historical/active session record, quick or scheduled). `SessionManager` unions the blocked apps/domains across every currently-active quick session + schedule before calling `AppBlocker.start`/`ActiveBlockList.domains =`.

### App/domain pickers

`InstalledAppsFinder` (`Knob/Features/Profiles/InstalledApp.swift`) scans `/Applications`, `/System/Applications`, `~/Applications` directly via `FileManager` rather than `NSMetadataQuery` — a deliberate simplicity tradeoff, not a placeholder. Domain blocking has no picker; `DomainListEditor` is free-text with light normalization (strips scheme/`www.`).
